1 · What this application is

A multi-tenant on-call scheduling and phone directory system for hospitals. It answers three questions:

  • Who is on call right now? — Dashboard, On-Call Schedule
  • How do I reach them? — Phone Directory
  • How do we page everyone at once in an emergency? — Command Center, Phone Trees

Around those sit staff administration, time-off approvals, duty-hour compliance reporting, and a HIPAA audit trail.

Tenant in this app means a hospital or facility — it is the data isolation boundary. A department such as Cardiology or Emergency Medicine sits inside a tenant.

2 · Before you start

Prerequisites

  • .NET 8 SDK
  • Node.js 18 or later
  • No database setup needed locally — development uses a SQLite file created on first run

The thing that confuses everyone: two authentication modes

The frontend and the backend each decide independently whether to use real sign-in or development sign-in. They must agree. As of 28 August 2026 the repository ships them agreed, on real sign-in.

SideSettingFile
FrontendVITE_DEV_AUTHsrc/frontend/.env (true), overridden by .env.local (false)
BackendDevAuth:Enabledappsettings.Development.json (false)

Development mode — both set to dev auth. You are signed in automatically as dev@local with full administrator rights, no Microsoft or Google account required. An amber banner reads “DEVELOPMENT AUTH — you are not really signed in.” Use this to explore the app.

Real sign-in mode — both set to real auth. You sign in with Microsoft or Google, and a brand-new account gets no access at all until an administrator grants it. That is correct behaviour, not a bug.

Do not mix the two

With the frontend on real sign-in and the backend on dev auth, the backend ignores your token entirely and treats every request as a full administrator. This is exactly what once made a brand-new Google account appear to hold “All Tenants” super-admin rights. A banner and a server log warning make it visible.

The setting is not the only switch

Properties/launchSettings.json set DevAuth__Enabled=true as an environment variable on the default profile, and environment variables outrank appsettings.Development.json. Turning dev auth off in the config file therefore did nothing — the app still authenticated every request from a cookie as a full administrator while the file plainly read false. That override has been removed, so the config file is now the single switch.

Do not confirm this by reading configuration. Confirm it by behaviour: with dev auth off, a request carrying only Cookie: X-Dev-Role=admin must return 401.

Real Entra sign-in needs one local value

appsettings.json ships placeholder Entra settings (ClientId: your-api-client-id). Dev auth replaced the whole pipeline, so nothing ever read them. With real auth on, the backend validates your genuine token against that placeholder and refuses it — IDX10214: Audience validation failed in the log. Set the real AzureAd:ClientId and AzureAd:Audience in appsettings.Development.json, matching VITE_AZURE_CLIENT_ID in the frontend. A client id is public, not a secret, and that file is gitignored regardless.

To explore the app with no account at all, set VITE_DEV_AUTH=true in src/frontend/.env.local (or delete that file) and restart the frontend — Vite only reads env files at startup — then set DevAuth:Enabled back to true and restart the backend. Both halves, or you have mixed the two.

To hold administrator rights under real sign-in, add your address to Authentication:SuperAdmins:Emails in appsettings.Development.json and restart the backend. It is matched by email across Entra, Google and local accounts, so one entry covers whichever provider you sign in with. Empty the list again to see the app as a brand-new user sees it.

3 · Starting the application

Two terminals. Backend first, because the frontend proxies to it.

# Terminal 1 — API on http://localhost:5000
cd src/backend/OnCallApi
dotnet run --urls "http://localhost:5000"

# Terminal 2 — web app on http://localhost:5173
cd src/frontend
npm install     # first time only
npm run dev

Expected outcome: http://localhost:5173 loads. In development mode you land on the Dashboard as dev@local. In real sign-in mode you get a login screen offering Microsoft and Google.

Verify the API independently with curl http://localhost:5000/api/auth/me — it returns your identity, permissions, tenantIds, authMode and sessionTimeoutMinutes.

Before testing anything that pages people

Twilio is enabled with a real sender number in appsettings.Development.json. Starting a code call sends real SMS and voice calls. Run locally with dispatch off:

Dispatch__Twilio__Enabled=false dotnet run --urls "http://localhost:5000"

Import rules — read before importing

The importer accepts CSV and Excel .xlsx. The format is decided by the file’s content, never its extension, so a workbook saved or renamed as .csv — the commonest way a real export arrives — imports correctly. The canonical headers are:

azureAdObjectId,firstName,lastName,email,title,
officePhone,mobilePhone,officeLocation,departmentId
  • firstName, lastName and email are required; the rest optional.
  • All or nothing — one bad row and nothing is imported.
  • Re-importing the same people updates them rather than creating duplicates.
  • Columns you leave out are untouched. A blank cell in a column you do include clears that value.
  • Messy phone formats are fine — (202) 555-0134, 202-555-0134, +1 202 555 0134. A number too short to dial is refused rather than stored, because an undialable number in the directory is worse than an empty field.
  • Everyday headings work too. Matching ignores case, spaces, underscores and hyphens, and understands common synonyms, so First Name, Work Email, Job Title, Work Phone, Cell and Work Location all land correctly.
  • Columns it does not recognise are ignored, not rejected — an export carrying Salary, Manager and Address imports the fields that matter and drops the rest.
  • Error lists are capped at 25, with the true total reported alongside.
  • A file that is not a spreadsheet still produces one error per line. An earlier draft of this guide claimed a single explanatory sentence instead; that is not what happens. Plain text reports a column-count mismatch, and a PDF reports a missing name on every line. The message will not tell you the file type is the problem — if you see an error on every row, check the file before checking the data.
  • Email addresses are not validated on import, although they are when you add one person by hand. A row reading NOT-AN-EMAIL imports cleanly and the record is created (limitation 18).

Download Template remains the surest starting point, but an HR export now usually imports as-is. A 30-row hospital export headed First Name / Work Email / Work Phone, saved as .xlsx but named .csv, imports 30 of 30 with no errors.

Departments are the one column still done by hand

Exports name a department (“Cardiology”); the importer wants the numeric departmentId. Rather than fail every row, the column is ignored — so staff import cleanly but arrive with no department set, and department-scoped on-call lookups will not find them until it is filled in.

On-Call Schedule Verified

Create schedules per department, generate rotations, assign shifts, handle swaps.

Expected outcome: generating shifts produces a rotation with a primary clinician on call at every hour, overnight included. A fortnight generated across three clinicians gave 28 shifts covering all 336 hours with no gap and no overlap. A swap must be approved before it takes effect, and ownership transfers only on approval.

Two details the wording used to gloss. A schedule requires a department in the sense that it crashes without one — a missing or unknown departmentId returns a 500 from an unhandled database error rather than a validation message (limitation 19). And .ics export is generated in the browser; there is no calendar endpoint on the server, so it cannot be driven by an integration.

Command Center Do not trust the screen

The live emergency view: active incidents, dispatch progress, and who has acknowledged.

This screen misreports a failed code call

The backend handles a failed dispatch correctly. With no channel configured it marks the incident failed, leaves it unacknowledged, and records “DISPATCH FAILED — no dispatch channel is configured, so nobody was contacted. Escalate by phone now.”

None of that reaches the operator. The four dead channels are drawn as pulsing amber pills — the same treatment used for a page in progress — and they pulse indefinitely. The failure text is never rendered anywhere in the page. Below them the pipeline log shows a fixed line reading “Awaiting activation. All paging channels nominal.”

So a code call reaching nobody looks like a code call in progress, with an explicit reassurance that paging is healthy. Until limitation 1 is fixed, confirm every code call by phone. Do not use this screen as evidence that anyone was reached.

How to exercise it safely

Starting a code call pages real clinicians by SMS and voice. The dispatch pipeline was tested on 28 August 2026 with all five channels force-disabled and Twilio credentials blanked, which is the only safe way to drive it. Consent gate, acknowledge, debrief, participants, resolve and idempotency all behaved correctly. The channel-success paths remain untested — nothing here confirms that a real page is delivered.

Phone Trees Verified

Escalation chains for emergencies: an ordered list of people to reach, each with a timeout before the next is tried. Reachable only at /dashboard/phone-trees — there is no sidebar link (limitation 5).

Expected outcome: the full editor works. Creating, renaming and deleting a tree, and adding, editing and reordering the people in it, all behave correctly end to end. Reordering two nodes swaps their positions and persists.

The trees that ship are empty

All seven seeded emergency trees — Code Blue, Red, Green, Silver, Grey and Pink — contain no people at all, and belong to no department. Opening Code Blue says so plainly: “No nodes configured.”

Both halves matter. An empty tree has nobody to escalate to. A tree with no department cannot be matched to a hospital, so its code calls produce no live updates on Command Center at all — and the New Code form has no department field, so trees created here inherit the same fault. Build your trees with a department set, and put people in them, before relying on either screen (limitations 2 and 3).

Time Off Verified, with a gap

Request time off; approve or deny as a manager.

Expected outcome: approving twice, denying after approval, or editing an approved request are each refused with an accurate message. All of those hold.

Administrators can approve their own time off

This guide previously said you cannot approve your own request. That is true for ordinary users — a viewer and a scheduler are both refused — but any administrator, including a tenant sub-admin, can approve their own request, and the record then names them as their own approver. If you rely on separation of duties for duty-hour or payroll audit, this is the gap (limitation 17).

Compliance Verified

Duty-hour rules — maximum hours per period, minimum rest between shifts, maximum consecutive days — and the violations found against them.

Expected outcome: the violations table lists breaches with employee, rule and date. Export downloads a CSV. The page occasionally returns a server error on load; reloading clears it (limitation 8). The cause is contention: twelve simultaneous requests all succeed, sixty produce ten failures, because the page writes data while being read.

Escalation Verified

Policies governing what happens when an on-call clinician does not acknowledge in time. Reachable only at /dashboard/escalation — no sidebar link (limitation 5).

Expected outcome: creating, editing and deleting a policy all work, and the Event Log records what the escalation engine did. The engine runs: test policies generated 40 events. Every one of them recorded a failed notification, which is the visible consequence of the dispatch channels being unconfigured — escalation decides who to reach next, but the reaching itself still depends on a working channel.

The form guards its own inputs, but the API behind it does not: a negative or zero response time is accepted if sent directly (limitation 11).

Settings Verified

Microsoft 365 integration status, notification toggles, schedule defaults, and the HIPAA session timeout (default 15 minutes).

The browser warns “Still there?” about a minute before signing you out.

The server-side cap covers local accounts only

This guide previously said the server independently caps token lifetime, so a captured token cannot outlive the policy. That cap exists — but only where the application mints the token itself, which means local accounts. Microsoft Entra and Google set their own token lifetimes, and nothing here shortens them. For those providers the session timeout is a browser-side policy, not a server-enforced one. Treat that as a real difference when writing up HIPAA session controls.

Public schedule links Broken

A shareable read-only coverage link at /on-call/{token}, created under Admin → Public Schedule.

This feature does not work at all

Every valid link returns a server error, with or without shifts behind it. The visitor sees “Link unavailable.” Creating and disabling links works; only viewing one fails, which is why it went unnoticed. The fault is in how the query is written rather than in any data, so it fails on Azure SQL exactly as it does locally — this is not a local-only problem (limitation 16).

It also defeats the privacy guarantee this guide used to claim. A valid token errors while an invalid one returns a clean not-found, so the two are trivially distinguishable and a link can be probed. The intended behaviour — coverage counts only, with no names, phone numbers or email addresses, and identical responses for unknown, disabled and expired tokens — is correctly written and will hold once the error is fixed. Do not hand out a share link until then.

6 · Who can do what

Permissions are granted per person, per tenant. A newly signed-in user has none until an administrator grants them under Admin → Users & Permissions.

PermissionGrants
Schedule.Read / WriteView / edit schedules and shifts
Directory.Read / WriteView / edit the phone directory
CodeCall.WriteManage code-call locations and direct messaging. Despite the name, this is not what guards starting a code call — see below
Admin.ScopedAdminister your own tenant
Admin.FullAdminister every tenant
Tenant.ManageCreate tenants and assign tenant administrators

Admin.Full, Admin.Scoped and Tenant.Manage cannot be handed out through the permissions UI, by design. They come only from the configured super-admin list or an explicit tenant-admin assignment. This holds under test: asking for Schedule.Write and Admin.Full together quietly grants only Schedule.Write.

Starting a code call is authorised by Schedule.Write

The endpoint that actually dispatches a code call checks Schedule.Write, not CodeCall.Write. So anyone who can edit a schedule can page real clinicians.

This undoes a safeguard elsewhere. Permissions granted automatically through Entra group membership deliberately exclude CodeCall.Write, on the stated reasoning that paging clinicians should never be acquired as a side effect of being added to a directory group. But that same automatic set includes Schedule.Write — which is the permission dispatch really checks. Until this is reconciled, treat Schedule.Write as carrying the authority to page (limitation 4).

7 · Known limitations

These need resolving before this document becomes official. They are numbered so they can be referenced directly, and the numbering changed on 28 August 2026 when the safety-critical group was added at the top — references elsewhere in this guide have been updated to match.

Safety-critical

  1. Command Center presents a failed code call as one in progress. When dispatch reaches nobody, the backend records the failure correctly and the screen shows none of it: dead channels pulse amber as though paging, indefinitely, above a fixed line reading “All paging channels nominal.” The failure text is never rendered. An operator has no way to tell a working code call from one that contacted no one. Until this is fixed, confirm every code call by phone.
  2. Every seeded emergency phone tree is empty. All seven — Code Blue, Red, Green, Silver, Grey, Pink — contain no people, so there is nobody to escalate to.
  3. Every seeded emergency phone tree has no department, which silences live updates. Real-time incident updates are matched to a hospital through the tree’s department. With none set, the update is correctly withheld rather than risk crossing tenants — so Command Center receives nothing for exactly the trees an emergency would use. The New Code form has no department field, so trees created in the app inherit the fault. Compounds limitation 1: no updates arrive, and their absence is drawn as paging in progress.
  4. Starting a code call is authorised by Schedule.Write, not CodeCall.Write. Anyone who can edit a schedule can page real clinicians — including anyone granted that permission automatically through Entra group membership, which is the exact route the withholding of CodeCall.Write was meant to close.

Blocking for a new user

  1. Phone Trees and Escalation have no sidebar link. Two whole features are reachable only by typing the URL.
  2. Imported staff arrive with no department. Exports name departments rather than numbering them, so the column is ignored and each person must be assigned afterwards. Until then they are missing from department-scoped on-call lookups.

Functional gaps

  1. Accounts created through the app cannot act as themselves. An employee added without an Entra object id cannot acknowledge a shift, request time off, or request a swap. On the Time Off page this surfaces as an unhandled error in the browser console rather than an explanation on screen.
  2. Compliance intermittently errors on load. Reloading clears it. Concurrent requests race on the same rows, because the page writes data during a page view.
  3. Timestamps with a non-UTC offset are stored incorrectly, off by the server's offset. The web app is unaffected because it always sends UTC; an EHR or mobile integration would not be.
  4. Presence sync cannot be switched off and retries a misconfigured Microsoft Graph endpoint every minute, which has stalled the API under load.
  5. Escalation policies and phone-tree nodes accept nonsensical values — a negative response time causes every unacknowledged shift to escalate immediately, and a node timeout can be set negative or zero. The web app blocks all of these; the API accepts them.
  6. Bulk import writes no per-record audit entry, which is thin against a six-year HIPAA retention requirement.
  7. The two tenant-admin roles are identical. Department Admin and Scoped Super Admin both confer the same permissions, including the right to start a code call; the role is recorded and displayed but nothing authorises on the difference. Do not rely on Department Admin as a restriction.
  8. Settings are not tenant-scoped — one tenant's setting keys are visible to another.
  9. Reversed and overlapping date ranges are accepted by the API. The web app blocks these client-side.
  10. Public schedule links return a server error for every valid token. The feature is unusable, and because a valid token errors while an invalid one returns a clean not-found, a link can be probed — defeating the privacy guarantee the feature exists to provide. The fault is in the query, so it affects Azure SQL as well as local development.
  11. Any administrator can approve their own time off, including a tenant sub-admin, and is recorded as their own approver. Ordinary users are correctly refused.
  12. Bulk import does not validate email addresses, although adding one person by hand does. Invalid addresses enter the directory silently.
  13. Creating a schedule without a valid department crashes with a server error instead of returning a validation message.
  14. Editing an escalation policy overwrites its creation date, destroying record provenance on every edit — thin against a six-year retention requirement.
  15. A shift swap with no replacement can still be approved. The shift is marked swapped while its owner is unchanged. Coverage is not lost, but the state is misleading.

Not built yet

  1. Multi-file spreadsheet merge — uploading several files, auto-matching columns and de-duplicating people is designed but not implemented.
  2. No self-service signup. A new organization cannot create itself; an existing administrator must create the tenant and grant access. This is deliberate.

9 · Verification status

Verified on 27 August 2026 against the running application, and updated 28 August 2026: all ten pages render without console errors; the development-auth banner displays correctly at desktop and mobile widths with no horizontal overflow; template download, the import dialog, employee creation, duplicate-email rejection, input validation and phone normalization all behave as described here.

Backend behaviour for schedules, time-off, compliance, escalation, tenants and public share links was verified through the API rather than the browser.

Test suites at time of writing: backend 334 passing, frontend 32 passing.

Re-verified on 28 August 2026 after the authentication and import changes: real Microsoft and Google sign-in both reach /api/auth/me successfully; a request carrying only the dev-role cookie returns 401; a 30-row .xlsx HR export named .csv imports 30 of 30; and a tenant sub-admin loads Users & Permissions without error.

The 28 August feature pass

Every feature in section 5 was re-tested on an isolated stack — a second backend with its own copy of the database, driven through a browser — so the running application was never disturbed. All five dispatch channels were force-disabled and the Twilio credentials blanked; no page was sent to anyone.

The pass corrected ten claims in this guide. Two features were better than recorded: Phone Trees and Escalation both have complete, working editors, not the bare rendering previously noted. Three were worse: public schedule links do not work at all, administrators can approve their own time off, and Command Center misreports a failed dispatch. Twelve defects were recorded in total, four of them safety-critical and now listed first in section 7.

What has still never been tested

Stated plainly, because a guide that implies more coverage than exists is worse than one that admits the gap:

  • A real code call with a live channel. Delivery, acknowledgement callbacks and SIP fallback have never been exercised. Nothing in this guide confirms a page actually arrives.
  • Real Entra and Google sign-in through the UI. Feature testing ran under development auth. Token validation and audience checking are unverified beyond confirming that the live server rejects a development cookie.
  • Multi-tenant isolation. Testing ran as a full administrator throughout. That a scoped sub-admin is genuinely confined to its own tenant has not been proven.
  • Microsoft 365 integration diagnostics, deliberately skipped — those endpoints open live Graph and dispatch connections.
  • File downloads. The .ics export, compliance CSV and import template are generated in the browser; the buttons and the generating code were checked, but no downloaded file was opened.
  • Real-time updates end to end. The connection showed as offline throughout; the live-update finding in limitation 3 comes from server logs, not an observed update.
  • Dashboard counts. The page renders and calls the right endpoints, but its numbers were never reconciled against the database.
