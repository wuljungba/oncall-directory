1 · What this application is

A multi-tenant on-call scheduling and phone directory system for hospitals. It answers three questions:

  • Who is on call right now? — Dashboard, On-Call Schedule
  • How do I reach them? — Phone Directory
  • How do we page everyone at once in an emergency? — Command Center, Phone Trees

Around those sit staff administration, time-off approvals, duty-hour compliance reporting, and a HIPAA audit trail.

Tenant in this app means a hospital or facility — it is the data isolation boundary. A department such as Cardiology or Emergency Medicine sits inside a tenant.

2 · Before you start

Prerequisites

  • .NET 8 SDK
  • Node.js 18 or later
  • No database setup needed locally — development uses a SQLite file created on first run

The thing that confuses everyone: two authentication modes

The frontend and the backend each decide independently whether to use real sign-in or development sign-in. They must agree. As of 28 August 2026 the repository ships them agreed, on real sign-in.

SideSettingFile
FrontendVITE_DEV_AUTHsrc/frontend/.env (true), overridden by .env.local (false)
BackendDevAuth:Enabledappsettings.Development.json (false)

Development mode — both set to dev auth. You are signed in automatically as dev@local with full administrator rights, no Microsoft or Google account required. An amber banner reads “DEVELOPMENT AUTH — you are not really signed in.” Use this to explore the app.

Real sign-in mode — both set to real auth. You sign in with Microsoft or Google, and a brand-new account gets no access at all until an administrator grants it. That is correct behaviour, not a bug.

Do not mix the two

With the frontend on real sign-in and the backend on dev auth, the backend ignores your token entirely and treats every request as a full administrator. This is exactly what once made a brand-new Google account appear to hold “All Tenants” super-admin rights. A banner and a server log warning make it visible.

The setting is not the only switch

Properties/launchSettings.json set DevAuth__Enabled=true as an environment variable on the default profile, and environment variables outrank appsettings.Development.json. Turning dev auth off in the config file therefore did nothing — the app still authenticated every request from a cookie as a full administrator while the file plainly read false. That override has been removed, so the config file is now the single switch.

Do not confirm this by reading configuration. Confirm it by behaviour: with dev auth off, a request carrying only Cookie: X-Dev-Role=admin must return 401.

Real Entra sign-in needs one local value

appsettings.json ships placeholder Entra settings (ClientId: your-api-client-id). Dev auth replaced the whole pipeline, so nothing ever read them. With real auth on, the backend validates your genuine token against that placeholder and refuses it — IDX10214: Audience validation failed in the log. Set the real AzureAd:ClientId and AzureAd:Audience in appsettings.Development.json, matching VITE_AZURE_CLIENT_ID in the frontend. A client id is public, not a secret, and that file is gitignored regardless.

To explore the app with no account at all, set VITE_DEV_AUTH=true in src/frontend/.env.local (or delete that file) and restart the frontend — Vite only reads env files at startup — then set DevAuth:Enabled back to true and restart the backend. Both halves, or you have mixed the two.

To hold administrator rights under real sign-in, add your address to Authentication:SuperAdmins:Emails in appsettings.Development.json and restart the backend. It is matched by email across Entra, Google and local accounts, so one entry covers whichever provider you sign in with. Empty the list again to see the app as a brand-new user sees it.

3 · Starting the application

Two terminals. Backend first, because the frontend proxies to it.

# Terminal 1 — API on http://localhost:5000
cd src/backend/OnCallApi
dotnet run --urls "http://localhost:5000"

# Terminal 2 — web app on http://localhost:5173
cd src/frontend
npm install     # first time only
npm run dev

Expected outcome: http://localhost:5173 loads. In development mode you land on the Dashboard as dev@local. In real sign-in mode you get a login screen offering Microsoft and Google.

Verify the API independently with curl http://localhost:5000/api/auth/me — it returns your identity, permissions, tenantIds, authMode and sessionTimeoutMinutes.

Before testing anything that pages people

Twilio is enabled with a real sender number in appsettings.Development.json. Starting a code call sends real SMS and voice calls. Run locally with dispatch off:

Dispatch__Twilio__Enabled=false dotnet run --urls "http://localhost:5000"

Import rules — read before importing

The importer accepts CSV and Excel .xlsx. The format is decided by the file’s content, never its extension, so a workbook saved or renamed as .csv — the commonest way a real export arrives — imports correctly. The canonical headers are:

azureAdObjectId,firstName,lastName,email,title,
officePhone,mobilePhone,officeLocation,departmentId
  • firstName, lastName and email are required; the rest optional.
  • All or nothing — one bad row and nothing is imported.
  • Re-importing the same people updates them rather than creating duplicates.
  • Columns you leave out are untouched. A blank cell in a column you do include clears that value.
  • Messy phone formats are fine — (202) 555-0134, 202-555-0134, +1 202 555 0134. A number too short to dial is refused rather than stored, because an undialable number in the directory is worse than an empty field.
  • Everyday headings work too. Matching ignores case, spaces, underscores and hyphens, and understands common synonyms, so First Name, Work Email, Job Title, Work Phone, Cell and Work Location all land correctly.
  • Columns it does not recognise are ignored, not rejected — an export carrying Salary, Manager and Address imports the fields that matter and drops the rest.
  • A file that is not a spreadsheet at all gives one sentence naming the fix, rather than one error per line. Error lists are capped at 25, with the true total reported alongside.

Download Template remains the surest starting point, but an HR export now usually imports as-is. A 30-row hospital export headed First Name / Work Email / Work Phone, saved as .xlsx but named .csv, imports 30 of 30 with no errors.

Departments are the one column still done by hand

Exports name a department (“Cardiology”); the importer wants the numeric departmentId. Rather than fail every row, the column is ignored — so staff import cleanly but arrive with no department set, and department-scoped on-call lookups will not find them until it is filled in.

On-Call Schedule API verified

Create schedules per department, generate rotations, assign shifts, handle swaps.

Expected outcome: creating a schedule requires a department. Generating shifts produces a rotation with a primary clinician on call at every hour, overnight included. A swap must be approved before it takes effect. Schedules export as .ics for Outlook or Google Calendar.

Command Center Not exercised

The live emergency view: active incidents, dispatch progress, and who has acknowledged.

Why this was not tested

Starting a code call pages real clinicians by SMS and voice. Verify this feature only with dispatch channels disabled.

Phone Trees Renders

Escalation chains for emergencies: an ordered list of people to reach, each with a timeout before the next is tried. Reachable only at /dashboard/phone-trees — there is no sidebar link (limitation 3).

Time Off API verified

Request time off; approve or deny as a manager.

Expected outcome: you cannot approve your own request, but your manager can. Approving twice, denying after approval, or editing an approved request are each refused with an accurate message.

Compliance Verified

Duty-hour rules — maximum hours per period, minimum rest between shifts, maximum consecutive days — and the violations found against them.

Expected outcome: the violations table lists breaches with employee, rule and date. Export downloads a CSV. The page occasionally returns a server error on load; reloading clears it (limitation 5).

Escalation Renders

Policies governing what happens when an on-call clinician does not acknowledge in time. Reachable only at /dashboard/escalation — no sidebar link.

Settings Verified

Microsoft 365 integration status, notification toggles, schedule defaults, and the HIPAA session timeout (default 15 minutes).

The timeout is enforced in two places: the browser warns “Still there?” about a minute before signing you out, and the server independently caps token lifetime to the same value, so a captured token cannot outlive the policy.

A shareable read-only coverage link at /on-call/{token}, created under Admin → Public Schedule.

6 · Who can do what

Permissions are granted per person, per tenant. A newly signed-in user has none until an administrator grants them under Admin → Users & Permissions.

PermissionGrants
Schedule.Read / WriteView / edit schedules and shifts
Directory.Read / WriteView / edit the phone directory
CodeCall.WriteStart a live code call. This pages real clinicians
Admin.ScopedAdminister your own tenant
Admin.FullAdminister every tenant
Tenant.ManageCreate tenants and assign tenant administrators

Admin.Full, Admin.Scoped and Tenant.Manage cannot be handed out through the permissions UI, by design. They come only from the configured super-admin list or an explicit tenant-admin assignment.

7 · Known limitations

These need resolving before this document becomes official. They are numbered so they can be referenced directly.

Blocking for a new user

  1. Phone Trees and Escalation have no sidebar link. Two whole features are reachable only by typing the URL.
  2. Imported staff arrive with no department. Exports name departments rather than numbering them, so the column is ignored and each person must be assigned afterwards. Until then they are missing from department-scoped on-call lookups.

Functional gaps

  1. Accounts created through the app cannot act as themselves. An employee added without an Entra object id cannot acknowledge a shift, request time off, or request a swap.
  2. Compliance intermittently errors on load. Reloading clears it. Concurrent requests race on the same rows, because the page writes data during a page view.
  3. Timestamps with a non-UTC offset are stored incorrectly, off by the server's offset. The web app is unaffected because it always sends UTC; an EHR or mobile integration would not be.
  4. Presence sync cannot be switched off and retries a misconfigured Microsoft Graph endpoint every minute, which has stalled the API under load.
  5. Escalation policies accept nonsensical values — a negative response time causes every unacknowledged shift to escalate immediately.
  6. Bulk import writes no per-record audit entry, which is thin against a six-year HIPAA retention requirement.
  7. The two tenant-admin roles are identical. Department Admin and Scoped Super Admin both confer the same permissions, including the right to start a code call; the role is recorded and displayed but nothing authorises on the difference. Do not rely on Department Admin as a restriction.
  8. Settings are not tenant-scoped — one tenant's setting keys are visible to another.
  9. Reversed and overlapping date ranges are accepted by the API. The web app blocks these client-side.

Not built yet

  1. Multi-file spreadsheet merge — uploading several files, auto-matching columns and de-duplicating people is designed but not implemented.
  2. No self-service signup. A new organization cannot create itself; an existing administrator must create the tenant and grant access. This is deliberate.

8 · Troubleshooting

“Your session wasn’t accepted”The API answered and refused the token — not an outage. Either the session expired (sign in again) or the API validates a different application or tenant than you signed in to. Check AzureAd:ClientId against VITE_AZURE_CLIENT_ID, and the log for IDX10214

9 · Verification status

Verified on 27 August 2026 against the running application, and updated 28 August 2026: all ten pages render without console errors; the development-auth banner displays correctly at desktop and mobile widths with no horizontal overflow; template download, the import dialog, employee creation, duplicate-email rejection, input validation and phone normalization all behave as described here.

Backend behaviour for schedules, time-off, compliance, escalation, tenants and public share links was verified through the API rather than the browser. The Command Center dispatch path was deliberately not exercised, because it pages real people.

Test suites at time of writing: backend 334 passing, frontend 32 passing.

Re-verified on 28 August 2026 after the authentication and import changes: real Microsoft and Google sign-in both reach /api/auth/me successfully; a request carrying only the dev-role cookie returns 401; a 30-row .xlsx HR export named .csv imports 30 of 30; and a tenant sub-admin loads Users & Permissions without error. Command Center dispatch remains deliberately unexercised, because it pages real people.
